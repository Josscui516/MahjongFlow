## 当前流程与权限

- 授权人员在活动详情的 **QR registration entry** 设置报名窗口并生成活动专属二维码。新链接为 `/register/[token]`；旧 `/check-in/[token]` 保留为报名入口别名，旧链接仍受撤销与时间窗口控制。
- 未登录参与者填写姓名、邮箱、活动要求的学号，并同意最小资料用于活动报名。第一次提交原子创建参与者和报名；重复提交不重复创建，不恢复工作人员已取消的报名，也不改写既有身份资料。
- 自助报名只写报名事实，不写签到、不加入晚餐名册。工作人员仍可独立管理实际签到。
- 每个活动有独立 `dinner_roster`。只有同时拥有 authorised 角色和账号管理能力的活跃管理员能录入、恢复和移除成员；其他 authorised 人员可核验，committee／匿名不能读取明细。
- 活跃晚餐名册成员具有资格，即使没有活动报名或签到；移除的成员无资格。姓名／邮箱仅用于名册识别。名册没有参与者／报名／签到外键，不会因其他流程变化自动修改。
- 录入入口：活动详情 → **Verify dinner eligibility** → **Manage dinner roster**。移除采用失活而非删除，可用同一邮箱重新录入恢复。该功能不记录实际领餐次数。

## 迁移、已有数据与回退

先部署 `20261004061203_separate_public_registration_and_dinner_roster.sql`，再发布引用新表与 RPC 的应用；生成类型由本地 Supabase CLI 重新生成。新表默认无名册，不从历史签到导入任何资格。历史报名和签到记录原样保留。

公开报名由只能授予 service_role 的窄 `submit_event_registration` RPC 执行。数据库再次验证活动 token、状态、窗口、字段及隐私同意，按邮箱串行化以防并发重复。浏览器不获得管理密钥，应用入口继续限制请求大小、输出与尝试频率。

报名的 `recorded_by` 改为可空，公开报名为 null；原后台写入触发器及 RLS 仍要求并设置真实后台操作者，不能冒称工作人员。晚餐名册有活动／录入者外键、活动加邮箱唯一约束、字段约束、默认拒绝 RLS 和受限列写权限。

回退时先撤下公开报名及名册管理入口，通过新前向 migration 撤销新 RPC／表权限，保留资料备份和新表。不得把新名册恢复成签到推导资格。已有公开报名的 null 录入者不能直接重新施加 NOT NULL；不得编造后台操作者或删除这些报名来满足旧约束。确认保存与业务决定后才能清理结构。

## 本地验证

真实本地 Auth／PostgREST／RLS 验证：首次报名、并发重复、学生证要求、隐私同意、无效／过期／撤销 token、工作人员取消后不能重启、报名不产生签到、签到不产生晚餐资格、管理员名册预录／重复录入／移除、授权非管理员写拒绝、committee／匿名明细拒绝。

浏览器验证：实际生成二维码、新用户手机尺寸报名、重复提交、后台名单显示、独立晚餐名单、管理员录入与移除、授权人员只能核验。仅使用虚构资料。
