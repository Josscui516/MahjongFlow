# 扫码提交即确认签到：2026-10-20 修正

## 用户确认的流程

参与者扫码后自行填写姓名、邮箱和需要的学号并提交，即完成本场确认签到；工作人员手动录入只是相同签到事实的备用入口，不需要再审核／确认一次。首次参与者同时建立报名与签到，已经报名但没有签到的参与者可通过原二维码补上签到。该决定替代先前「公开扫码只报名，工作人员再手动签到」的解释。

通用晚餐资格继续由独立名册决定。扫码确认签到后，匹配通用名册且报名有效的参与者可直接出现在本场晚餐领取名单；不匹配名册也可完成活动签到，但不会因此获得通用晚餐资格。活动发放勾选保持独立，不自动标记已领取。

继续关联 Issue #102 和 PR #103，独立于二维码权限 PR #101；本修复不调整活动删除或账号角色。用户提供的原活动数据未被自动改写，不把历史报名批量推断为签到。

## 实现与边界

新增 migration `20261020011407_confirm_attendance_on_public_qr_submission.sql`，提供只授予 service_role 的 `submit_event_self_check_in`，应用现有服务器入口调用它。浏览器不能直接调用提升权限的函数，仍经请求校验、大小限制和数据库限速；token、活动 Scheduled 状态、有效窗口、身份一致性、学号要求及隐私同意仍由数据库验证。

新函数在同一事务中复用 registration-only primitive 的验证与身份锁，然后生成 confirmed／qr 签到，recorded_by 为空，时间由数据库生成。任一步失败不留下新报名却没有签到的半完成结果。并发与重复扫描只产生一次签到；已有 confirmed 签到保持原方法、时间和操作者，返回已处理。

工作人员取消的报名不恢复。工作人员撤销的签到也不被公共重扫恢复，参与者收到联系工作人员的安全提示。若已有手工撤销签到而没有报名，新函数会回滚本次临时创建的报名，不留下意外写入。

原 `submit_event_registration` 保留为内部仅报名 primitive；普通后台报名与签到仍可单独操作。公开 `/register/[token]`、旧 `/check-in/[token]` 及其 API 兼容入口均继续可用，无需重生成二维码。界面改为 **Confirm check-in**，成功明确告知到场已确认，二维码管理区也说明无需再手动签到。

## 部署、已有记录与回退

在目标库按时间顺序应用所有待执行迁移，包括上述新函数迁移，再发布／重建前端。已有库不能 reset，Docker 重建不会自动升级函数。生成类型由 CLI 更新，新函数没有新增表或改变外键、唯一约束、索引和 RLS 策略。

原本仅报名的记录保持原样，不编造历史到场时间。参与者重新扫描仍有效的原二维码并提交，可在保留原报名的情况下写入当前真实签到。工作人员已有更正仍优先；已有签到、晚餐资格和发放记录不重写。

回退时先发布旧前端入口，再通过前向迁移撤销新函数 execute／删除未使用函数；保留已经确认的签到及其 QR 来源，不能为了回退而删除签到或发放记录。回退应用会恢复旧的两步解释，需业务负责人确认。
