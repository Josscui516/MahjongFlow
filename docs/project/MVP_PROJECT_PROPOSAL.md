# MahjongFlow MVP 项目企划书

> 面向 Monash Mahjong Club 的轻量级会议、任务与活动协调系统
>
> 项目周期：9 个开发周（课程第 2 周至第 10 周）
>
> 文档状态：MVP 开发基线
>
> 版本：1.0
> 编制日期：2026-08-02

## 1. 项目摘要

MahjongFlow 是一个供 Monash Mahjong Club 委员会内部使用的轻量级 Web 系统。项目要解决的核心问题不是建立一套通用企业项目管理平台，而是将目前分散在会议记录、群聊、Google Sheets、Google Forms 和人工签到中的工作连接成一条可追踪的流程：

```text
会议记录 → 决策转任务 → 活动筹备 → 报名与签到 → 晚餐资格核验 → Dashboard 跟进
```

本企划书将原项目规划收敛为一个可在 9 周内完成、部署并演示的 MVP。MVP 优先验证三个项目假设：

1. 委员会成员能否通过“会议决策转任务”减少会后遗漏；
2. 任务、负责人、截止日期和活动进度集中展示后，团队协作是否更透明；
3. 报名、实际签到和晚餐资格建立关联后，活动现场核验是否更准确。

## 2. 项目背景与问题

麻将社定期组织周常麻将活动，并在每学期举办比赛或其他特殊活动。委员会成员需要同时处理会议、场地、器材、宣传、报名、签到和晚餐安排。当前信息分散在多个工具中，造成以下问题：

- 会议中未完成的讨论或决策在会后容易被遗忘；
- 任务负责人、截止日期和完成状态缺少统一记录；
- 活动筹备任务、报名人数和实际到场人数彼此分离；
- 免费晚餐资格主要依赖人工查表，现场核验效率和准确性有限；
- 敏感的参与者与签到数据需要与一般委员会信息分开授权；
- 通用项目管理工具功能过重，需要大量配置，难以贴合社团的固定工作流。

## 3. MVP 目标

### 3.1 产品目标

在 9 周内交付一个可部署、可演示、具备基本权限保护的 Web MVP，使委员会能够：

- 登录并根据角色访问功能；
- 创建和查阅会议记录；
- 将会议决策转换为带负责人和截止日期的任务；
- 查看本人及全体委员会的待办、临期和逾期任务；
- 创建周常活动或比赛，并将筹备任务关联到活动；
- 维护参与者报名与实际签到状态；
- 通过活动专属 QR 入口完成签到；
- 由授权人员根据有效签到记录核验晚餐资格；
- 从 Dashboard 查看近期活动、待办、逾期任务和活动筹备进度。

### 3.2 项目管理目标

- 课程第 3 周结束前建立可持续开发的系统基础；
- 课程第 5 周完成“会议 → 决策转任务”流程，并进行唯一一次开发期 Stakeholder 阶段评审；
- 课程第 6 周结束前完成“会议 → 任务 → Dashboard”核心闭环；
- 课程第 8 周结束前完成“活动 → 报名 → 签到 → 晚餐核验”核心闭环；
- 课程第 9 周完成集成测试、权限测试和团队内部验收；
- 课程第 10 周完成修复、部署、文档与交接；
- 系统全部完成并通过内部验收后，再安排最终 Stakeholder 评审；
- 从课程第 4 周起始终保持一个可运行的集成版本，避免在最后一周集中集成。

## 4. 成功标准

MVP 满足以下条件时视为交付成功：

| 编号 | 成功标准 | 验证方式 |
|---|---|---|
| S1 | 委员会成员可创建会议，并在之后重新打开和更新记录 | 会议 CRUD 场景测试 |
| S2 | 一项会议决策可转为任务，且任务保留原会议链接 | 端到端功能测试 |
| S3 | 任务可记录负责人、截止日期和状态，并正确识别逾期 | 边界日期与状态测试 |
| S4 | Dashboard 可显示近期活动、待办、临期和逾期任务 | Dashboard 验收测试 |
| S5 | 活动可关联报名、筹备任务和签到记录 | 数据关系测试 |
| S6 | 同一参与者在同一活动中不能产生重复签到 | 数据库约束与重复提交测试 |
| S7 | 只有秘书或授权角色可以查看敏感签到和晚餐核验数据 | RBAC/RLS 权限测试 |
| S8 | 晚餐资格只能由已签到状态产生，未签到者不能被自动标记为符合资格 | 业务规则测试 |
| S9 | 5 名左右目标用户中至少 4 名可在少量指导下完成核心流程 | 可用性走查 |
| S10 | 系统在测试环境和正式演示环境均可从干净配置成功启动 | 部署与交接验证 |

## 5. 用户与角色

### 5.1 委员会成员

可访问一般协调信息，包括会议、任务、活动和非敏感进度信息。考虑到麻将社委员会规模较小且成员通常身兼多职，MVP 不再细分 President、Event Organiser、Promotion Lead 等业务角色；所有委员会成员对非敏感协调数据拥有相同的创建、查看和更新权限。

### 5.2 秘书／授权人员

在委员会成员权限之上，可访问参与者报名、签到明细和晚餐资格核验功能。该权限默认授予秘书；如实际活动需要，可由系统维护者向指定委员会成员授予 `authorised` 权限。

### 5.2.1 账号管理员能力

账号管理是独立于 `committee`／`authorised` 数据访问角色的能力。具备
`can_manage_accounts` 的当前委员会成员可以在应用内邀请、更新、停用和恢复其他
委员会账号，并可以授予或撤销 `authorised` 与账号管理能力。账号管理员不因该
能力自动获得参与者敏感数据访问权；系统必须阻止其停用自己、撤销自己的账号
管理能力或移除最后一名有效账号管理员。

### 5.3 活动参与者

无需进入委员会后台，只能通过受限页面完成活动报名或活动现场签到。不能查看内部会议、任务或其他参与者资料。

### 5.4 MVP 权限原则

- 权限必须由服务端和数据库共同执行，不能只隐藏前端按钮；
- 默认拒绝访问，明确授权后才开放敏感数据；
- 只收集报名和签到所必需的最少个人信息；
- 开发和演示使用虚构或匿名化数据；
- MVP 不提供任意自定义权限编辑器；数据访问仍使用预定义的 `committee` 与
  `authorised`，账号管理使用独立布尔能力；
- 角色与账号状态变更只能通过受保护的账号管理服务端入口和窄数据库函数完成，
  不允许浏览器直接更新 `profiles`；
- 所有角色变更必须记录操作者、变更对象和变更时间；如果首个版本来不及实现完整审计表，则至少保留数据库更新时间和变更记录。

### 5.5 MVP 权限矩阵

| 功能／数据 | 普通委员会成员 | 秘书／授权人员 | 活动参与者／未登录用户 |
|---|---|---|---|
| 登录委员会后台 | 允许 | 允许 | 禁止 |
| 查看、创建、更新会议 | 允许 | 允许 | 禁止 |
| 查看、创建、更新任务 | 允许 | 允许 | 禁止 |
| 查看、创建、更新活动基本资料 | 允许 | 允许 | 仅可查看公开活动资料 |
| 查看非敏感 Dashboard 汇总 | 允许 | 允许 | 禁止 |
| 查看报名人数和签到总数 | 允许，仅聚合数字 | 允许 | 禁止 |
| 查看参与者姓名、邮箱或学号 | 禁止 | 允许 | 仅能提交自己的资料，不能读取名单 |
| 创建或修改参与者报名记录 | 禁止 | 允许 | 仅在开放自助报名时提交自己的报名 |
| 查看签到明细 | 禁止 | 允许 | 禁止 |
| 执行人工补签或更正签到 | 禁止 | 允许 | 禁止 |
| 查看或确认晚餐资格 | 禁止 | 允许 | 只能获得自己的签到成功结果，不显示后台资格名单 |
| 使用活动 QR 签到 | 不适用 | 可代为处理 | 允许在有效签到窗口提交自己的签到 |
| 分配或撤销角色 | 仅具备账号管理能力时允许 | 仅具备账号管理能力时允许 | 禁止 |
| 邀请、停用或恢复委员会账号 | 仅具备账号管理能力时允许 | 仅具备账号管理能力时允许 | 禁止 |

权限实现规则：

- 普通委员会成员的活动页面只能查询聚合后的报名／签到数量，查询结果中不得包含个人字段；
- 秘书／授权人员访问敏感页面时，前端路由、服务端处理函数和数据库 RLS 必须同时验证角色；
- 参与者页面使用活动专属、可失效的 token，并只开放当前操作需要的最小接口；
- 未授权请求统一返回拒绝结果，不通过错误信息泄露参与者是否存在；
- 委员会成员离任或不再需要敏感访问时，应立即撤销账号或授权角色。

## 6. MVP 功能范围

### 6.1 P0：必须交付

#### A. 系统基础与身份认证

- 委员会账号登录和登出；
- 账号管理员邀请、查看、更新、停用和恢复委员会账号；
- 用户通过邀请或恢复邮件自行设置密码，管理员不能查看或指定其密码；
- 账号角色／状态变更审计与最后一名管理员保护；
- 会话保持与受保护路由；
- `committee` 与 `secretary/authorised` 两级角色；
- Supabase Row Level Security 或等效的服务端数据访问规则；
- 基础错误反馈、空状态和加载状态。

#### B. 会议管理

- 创建、查看和更新会议；
- 记录会议标题、日期、时间、参与者和摘要；
- 记录讨论点与关键决策；
- 查看历史会议；
- 删除功能不是 MVP 必需项，可使用归档或不提供删除。

#### C. 会议决策转任务

- 从讨论点或关键决策创建任务；
- 自动保存来源会议及来源决策；
- 填写任务标题、描述、负责人、截止日期和状态；
- 从任务页面返回来源会议；
- MVP 每项任务只设置一个主要负责人，以降低数据和界面复杂度。

#### D. 任务与 Dashboard

- 创建、查看和更新任务；
- 状态包括 `Not Started`、`In Progress`、`Completed`；
- `Overdue` 由系统根据截止日期和完成状态计算，不作为可任意选择的持久化状态；
- 按负责人、状态、截止日期和相关活动筛选；
- Dashboard 展示本人任务、全部待办、临期、逾期和近期活动；
- MVP 的提醒仅指站内视觉提醒，不包含邮件、短信或推送通知。

#### E. 活动管理

- 创建和更新 `Weekly Session` 与 `Tournament` 两类活动；
- 记录名称、日期、时间、地点、描述和状态；
- 将任务关联到活动；
- 展示活动筹备任务和简单完成进度；
- 查看即将到来的活动。

#### F. 报名、签到与晚餐核验

- 为活动记录最小化的参与者报名信息，字段按本节下方的数据最小化方案执行；
- 区分 `Registered` 与 `Attended`；
- 为每个活动生成专属签到 URL/QR；
- 签到入口只在指定活动和有效时间窗口内工作；
- 服务端验证活动、参与者和重复签到；
- 使用 `event_id + participant_id` 唯一约束防止重复记录；
- 授权人员可人工补签或纠正签到状态，并保留更新时间；
- 晚餐资格根据确认签到状态显示为 `Eligible` 或 `Not Eligible Yet`；
- 只有授权人员可查看签到明细和执行核验。

#### G. 最小参与者字段设计

参与者主记录只保存跨活动识别所需的最小信息：

| 字段 | 是否必填 | 可见角色 | 用途与约束 |
|---|---|---|---|
| `participant_id` | 系统生成 | 授权人员／系统 | 随机 UUID，作为内部主键，不向用户展示 |
| `full_name` | 必填 | 授权人员；本人提交时可见 | 活动现场身份确认；限制合理长度并去除多余空白 |
| `email` | 必填 | 授权人员；本人提交时可见 | 报名识别和防止重复记录；存储前标准化大小写 |
| `student_id` | 条件必填 | 仅授权人员 | 只有活动确实需要 Monash／MSA 身份或资助证明时才收集；普通活动留空 |
| `created_at` | 系统生成 | 授权人员／系统 | 记录建立时间 |
| `updated_at` | 系统生成 | 授权人员／系统 | 记录最近更新时间 |

报名记录保存以下字段：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `event_id` | 必填 | 关联活动 |
| `participant_id` | 必填 | 关联参与者 |
| `registration_status` | 必填 | `Registered`、`Cancelled`，默认 `Registered` |
| `registered_at` | 系统生成 | 报名时间 |
| `privacy_notice_acknowledged_at` | 自助报名时必填 | 记录参与者已看到数据用途说明；由授权人员代录时可为空 |

签到记录保存以下字段：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `event_id` | 必填 | 关联活动 |
| `participant_id` | 必填 | 关联参与者 |
| `checked_in_at` | 系统生成 | 实际签到时间 |
| `check_in_method` | 必填 | `QR` 或 `Manual` |
| `recorded_by` | 条件必填 | 人工补签／更正时记录授权用户；自助 QR 签到可为空 |
| `updated_at` | 系统生成 | 最近更正时间 |

数据最小化限制：

- 不收集电话号码、生日、住址、付款资料、紧急联系人或与本 MVP 无关的个人资料；
- 不为晚餐资格单独收集个人属性，资格仅由当前活动的有效签到状态计算；
- `student_id` 不作为所有活动的默认必填项；
- `email` 只用于身份匹配和防重复，MVP 不发送营销信息；
- 同一活动以 `event_id + participant_id` 约束报名和签到唯一性；
- 最终上线前由 Stakeholder 确认数据保留期限；在期限确认前，MVP 不实现永久保存承诺，并提供按活动清理测试数据的维护流程。

### 6.2 P1：有余量时交付

- 活动报名的公开自助页面；
- 活动报名与签到汇总导出为 CSV；
- 活动专属默认筹备清单；
- 简单活动复制功能；
- 更完整的审计记录；
- 移动端现场签到体验优化；
- 基础可访问性自动检查。

### 6.3 不属于本次 MVP

- 独立的宣传内容管理模块与多阶段审批流；
- Instagram、Facebook 或其他社交媒体直接发布；
- 邮件、短信、系统推送或外部日历集成；
- 高度可配置的活动模板系统；
- 多负责人、子任务和复杂任务依赖；
- 财务、支付、会员费、预算或赞助款管理；
- 麻将比赛计分、排名、对局或桌位分配；
- 实时聊天；
- 原生 iOS/Android 应用；
- 完整会员管理与长期会员档案；
- 高级报表、预测分析和企业级项目管理功能。

## 7. 核心用户故事与验收条件

### US-01：记录会议

作为委员会成员，我希望保存会议讨论和决策，以便会后能准确回顾。

验收条件：

- 必填字段缺失时不能提交，并显示清楚的错误信息；
- 保存后刷新页面，记录仍可正确读取；
- 允许添加多个讨论点和决策；
- 一般委员会成员可以查看会议，但不能访问敏感签到数据。

### US-02：从决策创建任务

作为委员会成员，我希望把会议决策直接转换为任务，以免行动项遗失。

验收条件：

- 可从某一决策打开创建任务表单；
- 创建后的任务保存来源会议和来源决策；
- 任务必须包含负责人和截止日期；
- 从会议页和任务页都能看到关联关系。

### US-03：跟进任务

作为委员会成员，我希望快速看到自己负责、临期和逾期的任务，以便安排工作。

验收条件：

- Dashboard 可显示本人未完成任务；
- 已过截止日期且未完成的任务自动显示为逾期；
- 完成任务后不再计入逾期；
- 筛选结果与 Dashboard 统计一致。

### US-04：筹备活动

作为活动组织者，我希望将活动资料和筹备任务集中管理，以便了解准备进度。

验收条件：

- 可创建周常活动或比赛；
- 活动可关联多个任务；
- 活动页显示相关任务及完成比例；
- 活动日期变更后，相关信息仍保持完整。

### US-05：登记报名和签到

作为授权人员，我希望区分报名者与实际到场者，以便生成准确的参与记录。

验收条件：

- 报名不会自动等同于签到；
- 有效参与者可通过活动 QR 入口签到；
- 重复提交不会产生第二条签到记录；
- 无效、过期或不属于该活动的签到请求被拒绝；
- 授权人员可在后台查看汇总和明细。

### US-06：核验晚餐资格

作为授权人员，我希望按实际签到核验晚餐资格，以减少错误发放。

验收条件：

- 已确认签到者显示为符合资格；
- 未签到者显示为暂不符合资格；
- 一般委员会成员和参与者无法访问核验明细；
- 人工修正签到后，资格结果同步更新。

## 8. 建议技术方案

### 8.1 技术栈

| 层级 | 建议方案 | MVP 采用理由 |
|---|---|---|
| Web 框架 | Next.js + TypeScript | 前后端可在同一项目内交付，减少多仓库和接口协调成本 |
| UI | React + Tailwind CSS | 适合快速构建响应式管理界面 |
| 数据库 | Supabase PostgreSQL | 支持关系数据、约束、迁移和托管服务 |
| 身份认证 | Supabase Auth | 与数据库和 RLS 集成，减少自建认证风险 |
| 权限 | Supabase RLS + 服务端鉴权 | 敏感考勤数据不能只靠前端控制 |
| 部署 | Vercel + Supabase | 适合学生项目和演示环境，运维成本低 |
| 版本管理 | GitHub + Pull Request | 支持审查、回滚和任务追踪 |
| 项目管理 | GitHub Projects/Kanban | 将需求、开发、测试和缺陷放在同一工作流中 |

技术栈在课程第 2 周结束前冻结。除非出现阻断性问题，9 个开发周内不更换核心框架、数据库或认证方案。

### 8.2 高层架构

```text
委员会后台 / 参与者受限页面
              │
              ▼
     Next.js Web Application
   UI + Server Actions/API Routes
              │
       ┌──────┴──────┐
       ▼             ▼
 Supabase Auth   PostgreSQL + RLS
                       │
                       ▼
 Meetings / Decisions / Tasks / Events
 Participants / Registrations / Attendance
```

### 8.3 建议核心数据实体

| 实体 | 关键字段／关系 |
|---|---|
| `profiles` | 用户、显示名、委员会职位、数据访问角色、账号管理能力与有效状态 |
| `account_management_audit` | 账号变更操作者、目标、动作、前后角色／状态与时间；不保存密码或 token |
| `meetings` | 标题、时间、参与者、摘要、创建者 |
| `discussion_points` | 所属会议、内容、顺序 |
| `meeting_decisions` | 所属会议、内容、是否已转任务 |
| `tasks` | 标题、描述、负责人、截止日期、状态、来源会议／决策、相关活动 |
| `events` | 类型、名称、时间、地点、描述、签到有效窗口、状态 |
| `participants` | 最少必要的参与者标识和显示名 |
| `registrations` | 活动与参与者的报名关系、报名状态 |
| `attendance_records` | 活动、参与者、签到时间、签到方式、修正者 |

关键约束：

- 一条任务最多关联一个来源会议决策，但可以不来源于会议；
- 一条任务最多关联一个活动；
- 同一参与者对同一活动只能有一条报名记录；
- 同一参与者对同一活动只能有一条签到记录；
- 晚餐资格是由签到状态计算得到的业务结果，不重复存储为可随意编辑的数据源。

### 课程第 7 周（开发第 6 周）：活动与报名

- 活动进度展示；
- 参与者与报名记录；
- 近期活动接入 Dashboard；

交付物：可管理活动、报名和筹备任务的页面。

### 课程第 8 周（开发第 7 周）：QR 签到与晚餐核验

目标：完成麻将社特有的现场业务闭环。

- 活动专属签到 token、URL 和 QR 展示；
- 签到有效窗口和服务端校验；

里程碑 M4：活动运营端到端流程完成。

### 课程第 9 周（开发第 8 周）：集成、内部验收与安全检查

目标：停止扩展功能，集中提高完整性和可靠性。

- RLS、服务端权限和公开入口安全检查；

## 10. 并行工作建议

为避免所有模块串行开发，团队可按以下工作流并行推进：

| 工作流 | 主要职责 |
|---|---|
| 产品与项目协调 | 范围、backlog、进度、依赖、stakeholder 验收与演示 |
| UI/UX 与前端 | 信息架构、组件、表单、页面、响应式和可用性 |
| 数据与后端 | 数据库、迁移、业务规则、API／Server Actions 和关系完整性 |
| 认证与权限 | Auth、RLS、服务端授权、公开入口安全与隐私检查 |
| 测试与文档 | 验收用例、集成测试、回归、缺陷管理、用户和部署文档 |

建议每个功能拥有一名主要负责人和一名审查人。代码完成不等于功能完成；只有通过审查、测试并合入可部署分支后，任务才能进入 `Done`。

## 11. 开发与协作流程

### 11.1 Kanban 状态

```text
Backlog → Ready → In Progress → Review → Testing → Done
```

- 每人同时处于 `In Progress` 的主要任务不超过 1 个；
- 开始任务前必须确认验收条件和依赖；
- 阻塞超过 1 个工作日必须在项目板上标记并在团队会议中升级；
- 每周进行一次计划／演示会议和一次短风险检查；
- 第 5、7、8 周安排正式里程碑评审。

### 11.2 分支与审查

- 每个功能或修复使用短生命周期分支；
- Pull Request 必须关联 issue 和验收标准；
- 至少一名其他成员完成审查；
- 涉及数据库或权限的更改必须包含迁移、回滚说明和权限测试；
- 禁止向仓库提交真实参与者数据、密钥或生产环境配置。

### 11.3 Definition of Done

功能只有同时满足以下条件才算完成：

- 对应用户故事和验收条件已满足；
- lint、typecheck、自动化测试和构建通过；
- 关键成功路径和失败路径已手动测试；
- 权限和隐私行为已检查；
- 数据关系和迁移已验证；
- 另一名成员已完成代码审查；
- 用户界面包含加载、空状态、成功和错误反馈；
- 相关文档已更新；
- 功能已部署到共享测试环境并完成演示。

## 12. 测试策略

### 12.1 自动化测试重点

- 逾期状态计算；
- 晚餐资格计算；
- 签到有效窗口；
- 重复报名和重复签到防护；
- 会议决策与任务的关联；
- 角色权限和未授权响应；
- 关键表单校验。

### 12.2 集成与端到端场景

1. 委员会成员登录；
2. 创建会议并记录一项决策；
3. 将决策转换为带负责人和截止日期的任务；
4. 创建活动并将任务关联到活动；
5. 添加参与者报名；
6. 参与者通过活动 QR 入口签到；
7. 授权人员查看签到并核验晚餐资格；
8. Dashboard 正确更新任务、活动和进度信息。

### 12.3 权限矩阵测试

至少使用三种会话进行验证：

- 普通委员会成员；
- 秘书／授权人员；
- 未登录参与者或匿名用户。

测试必须覆盖直接访问 URL、直接请求服务端接口和数据库策略，不仅检查页面上是否显示按钮。

## 13. 主要风险与应对

| 风险 | 可能性／影响 | 预警信号 | 应对措施 |
|---|---|---|---|
| 9 周时间不足 | 高／高 | 连续一周未达里程碑；PR 大量堆积 | 严格 P0；每周复盘；立即移除 P1；避免中途换技术栈 |
| 范围蔓延 | 高／高 | 新功能未关联 P0 验收标准 | 新需求进入 Post-MVP backlog，除非替换现有范围 |
| 前端、后端和数据库集成过晚 | 中／高 | 各模块只能在本地或 mock 数据运行 | 从课程第 3 周使用共享环境；每周合并并部署集成版本 |
| RLS 或权限错误 | 中／高 | 普通账号能读取签到明细 | 默认拒绝；权限矩阵测试；敏感查询集中审查 |
| QR 签到被重复或滥用 | 中／高 | 同一人多条记录；过期活动仍可签到 | 唯一约束、有效窗口、服务端校验、授权人工修正 |
| 用户认为系统过重 | 中／中 | 可用性测试中步骤过多 | 保留固定工作流和熟悉术语；不引入自定义配置中心 |
| 团队负载不均 | 中／中 | 同一成员长期阻塞多个关键模块 | 限制 WIP；设置审查人；按里程碑重新分配工作 |
| Stakeholder 反馈延迟 | 中／中 | 课程第 5 周评审或最终评审未确认 | 课程第 2 周预约课程第 5 周阶段评审；项目完成前提前预约最终评审；课程第 9 周由团队执行内部验收，不依赖 Stakeholder 到场 |
| 免费服务限制或部署故障 | 低／高 | 测试环境配额或构建失败 | 提前部署；监控配额；保留本地演示和数据库备份方案 |

## 14. 延期时的削减顺序

当里程碑延期时，必须削减范围而不是降低数据安全和测试标准。

按以下顺序移除或简化：

1. 移除 CSV 导出、活动复制和高级可访问性自动检查；
2. 移除公开自助报名，改为授权人员在后台登记报名；
3. 简化活动进度展示，只显示相关任务完成数；
4. 简化 Dashboard 图表，仅保留数字卡片和列表；
5. 简化 QR 签到界面，但保留活动 token、服务端验证和唯一约束；
6. 若 QR 流程仍无法稳定交付，保留授权人员现场手动签到作为最终降级方案，并将 QR 标记为下一版本首要事项。

无论进度如何，以下内容不得为了赶工而取消：

- 服务端身份和权限检查；
- 敏感数据访问限制；
- 数据库唯一约束和迁移；
- 会议决策到任务的可追踪关系；
- 核心端到端验收与回归测试。

## 15. 交付物

课程第 10 周结束时应提供：

- 可访问的 MahjongFlow MVP 演示环境；
- 完整源代码和可追踪的提交历史；
- 数据库迁移、RLS 策略和匿名化种子数据；
- `.env.example` 与干净安装步骤；
- 自动化测试和最终测试结果；
- 权限矩阵与隐私说明；
- 用户操作指南；
- 部署、维护和故障恢复说明；
- MVP 演示脚本；
- Post-MVP backlog 与已知限制清单。

## 16. MVP 之后的建议路线

MVP 经用户验证后，再根据真实使用反馈决定是否开发：

1. 活动模板和默认筹备清单；
2. 独立的宣传任务工作流；
3. 邮件、日历或其他外部提醒；
4. 更完整的导出和报表；
5. 委员会换届与权限交接；
6. 操作审计日志；
7. 对更多大学社团的可配置支持。

这些功能不应在 MVP 核心流程稳定前进入开发。

### 17.1 评审安排的执行规则

| 评审阶段 | 参与者 | 时间 | 评审内容 | 结果处理 |
|---|---|---|---|---|
| 阶段评审 | Stakeholder、项目团队 | 课程第 5 周（开发第 4 周） | 演示“会议 → 决策转任务”流程，确认其是否符合委员会的真实工作方式，并说明下一阶段的 Dashboard 方案 | 允许澄清或修正 P0 流程；新增能力进入 Post-MVP backlog。只有团队正式批准以等量替换现有范围时，新增能力才可进入本轮 MVP |
| 内部验收 | 项目团队 | 课程第 9 周（开发第 8 周） | 根据 RTM、权限矩阵和端到端场景，检查功能、权限、数据关系和阻断级缺陷 | Stakeholder 无需参与；未通过的 P0 项目必须在最终交付前修复 |
| 最终评审 | Stakeholder、项目团队 | 项目全部完成并通过内部验收后，预计在课程第 10 周结束后安排 | 评审完整 MVP、部署版本、核心流程和交付文档 | 阻断级缺陷进入交付修复；功能增强、体验优化和新增需求进入 Post-MVP backlog |

如果最终 Stakeholder 评审无法立即安排，已经通过内部验收的版本应保持为候选发布版。等待评审期间不得继续扩大功能范围。

基于以上批准事项，本文件自本次更新起正式作为 9 周 MahjongFlow MVP 的范围、排期、权限、数据最小化和验收基线。
