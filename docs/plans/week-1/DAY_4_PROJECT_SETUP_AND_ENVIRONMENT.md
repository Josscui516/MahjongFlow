# 第 4 天计划：项目骨架与开发环境搭建

## 1. 当日目标

建立可在本地启动、可连接 Supabase、可部署到 Vercel，并能由另一名成员从干净环境复现的项目骨架。本日只搭建基础设施，不实现业务功能。

## 2. 开始条件

- 技术栈、仓库结构和协作规则已经冻结；
- ERD、迁移顺序、权限矩阵和种子数据方案已经完成评审；
- GitHub、Supabase 和 Vercel 的项目访问权限已经准备好；
- 已明确开发环境与生产环境的配置隔离方式；
- 团队确认不得提交密钥、真实环境值或真实参与者数据。

## 3. 详细执行步骤

### 步骤 1：检查本地与远程前置条件

1. 确认 GitHub 仓库地址和默认分支；
2. 确认团队成员具有所需的仓库权限；
3. 确认本地 Node.js 与包管理器版本策略；
4. 确认 Supabase 开发项目及访问权限；
5. 确认 Vercel 团队或个人项目的创建权限；
6. 检查仓库现有文件，避免覆盖企划书和计划文档；
7. 记录实际采用的运行时和包管理器版本。

产出：环境前置条件检查记录。

执行记录：[第 4 天步骤 1：环境前置条件检查记录](artifacts/day-4/DAY_4_STEP_1_ENVIRONMENT_PREREQUISITE_CHECK.md)。当前本地、GitHub、版本策略、Supabase 与 Vercel 项目前置条件均已满足；仓库已转移到 `Josscui516`，Vercel 项目已连接。用户已确认 Week 1 Day 4 暂不要求 Issue。

检查：缺失权限或版本冲突已经解决，不会在初始化中途阻塞。

### 步骤 2：初始化应用骨架

1. 在现有仓库中初始化 Next.js 与 TypeScript 应用；
2. 启用 Tailwind CSS；
3. 选择与团队技术决策一致的路由方案；
4. 使用团队统一的包管理器；
5. 安装完成后启动开发服务器；
6. 在浏览器中打开初始页面并确认无运行错误；
7. 检查生成文件，没有覆盖已有项目文档；
8. 保存初始依赖锁文件。

产出：可以本地启动的 Next.js 项目。

执行记录：[第 4 天步骤 2：应用骨架初始化记录](artifacts/day-4/DAY_4_STEP_2_APPLICATION_SCAFFOLD.md)。已完成 Next.js App Router、TypeScript、Tailwind CSS、ESLint 和 npm 项目初始化；初始页面、lint、typecheck 和生产构建均已验证通过。

检查：开发服务器正常启动，初始页面可访问，终端无阻断错误。

### 步骤 3：落实仓库目录结构

1. 按第 1 天的仓库结构建立路由和布局目录；
2. 建立共享 UI 组件目录；
3. 建立业务模块、服务端逻辑、工具函数和类型目录；
4. 建立 Supabase 迁移、种子数据和策略目录；
5. 建立测试及测试辅助文件目录；
6. 建立架构、权限和运行文档目录；
7. 为尚未使用但需要保留的目录添加简短说明；
8. 核对实际目录与已批准结构是否一致。

产出：标准化项目目录骨架。

执行记录：[第 4 天步骤 3：仓库目录结构落实记录](artifacts/day-4/DAY_4_STEP_3_REPOSITORY_STRUCTURE.md)。已建立路由、共享组件、P0 feature、基础设施、类型、Supabase、测试和文档目录；未公开业务路由或提前实现数据库与权限功能。

检查：代码、数据库、测试和文档均有明确位置，不存在重复用途目录。

### 步骤 4：配置环境变量与安全忽略规则

1. 列出应用连接 Supabase 所需的变量名称；
2. 区分允许在浏览器使用的公开配置与仅服务端可使用的密钥；
3. 创建本地环境变量文件并填入开发环境值；
4. 创建只包含变量名和说明的 `.env.example`；
5. 检查 `.gitignore` 已忽略本地环境文件；
6. 搜索工作区，确认没有意外写入密钥；
7. 在 README 中说明每个变量的获取位置和用途，但不记录真实值。

产出：安全的本地环境配置、`.env.example` 和配置说明。

执行记录：[第 4 天步骤 4：环境变量与安全忽略规则记录](artifacts/day-4/DAY_4_STEP_4_ENVIRONMENT_AND_IGNORE_RULES.md)。变量合同、忽略规则、README 和操作说明已完成；Supabase 项目 URL 与 publishable key 已写入被忽略的 `.env.local` 并通过不回显值的安全检查。步骤 5 可以开始实现和验证真实连接。

检查：仓库可共享配置结构，但 Git 不会追踪任何真实密钥。

### 步骤 5：连接 Supabase 开发环境

1. 将应用配置指向专用 Supabase 开发项目；
2. 建立浏览器端和服务端所需的 Supabase 客户端基础封装；
3. 确保服务端密钥不会进入客户端代码；
4. 添加最小连接验证方式；
5. 启动应用并执行连接验证；
6. 检查错误处理不会在页面或日志中泄露密钥；
7. 记录本地连接步骤和常见失败原因。

产出：已连接 Supabase 开发环境的应用骨架。

执行记录：[第 4 天步骤 5：Supabase 开发环境连接记录](artifacts/day-4/DAY_4_STEP_5_SUPABASE_CONNECTION.md)。已建立 browser/server client 基础封装和无业务表依赖的健康接口；本地运行时连接返回 HTTP 200，lint、typecheck、build、audit 与浏览器检查均通过，且连接路径不读取或暴露 server-only secret。

检查：应用可验证服务可达，浏览器构建产物中不包含服务端密钥。

### 步骤 6：建立数据库迁移基线

1. 初始化项目约定的 Supabase 数据库目录；
2. 按第 3 天方案建立迁移文件命名规则；
3. 建立首个基线迁移或迁移占位结构；
4. 明确后续表、约束、RLS 和种子数据的执行顺序；
5. 建立本地应用迁移与重建数据库的说明；
6. 验证迁移文件能够被版本管理追踪；
7. 暂不实现第 2 周认证和业务表功能，避免越过本周范围。

产出：数据库迁移目录、命名规则和执行说明。

执行记录：[第 4 天步骤 6：数据库迁移基线记录](artifacts/day-4/DAY_4_STEP_6_DATABASE_MIGRATION_BASELINE.md)。已锁定 Supabase CLI `2.111.0`，由 CLI 生成空的 timestamped migration；本地 Docker 栈完成无 seed reset、migration list、database lint、schema diff 和范围查询，确认基线可重放且未创建业务表、类型或 RLS。

检查：团队知道如何新增、应用和审查迁移，且基线未提前引入业务功能。

### 步骤 7：创建 Vercel 预览环境

1. 将 Vercel 项目连接到 GitHub 仓库；
2. 确认框架和构建设置正确；
3. 在 Vercel 中配置开发／预览环境所需变量；
4. 触发首次预览部署；
5. 检查构建日志并修复配置问题；
6. 打开预览 URL 并确认页面正常；
7. 检查预览页面和日志没有暴露敏感配置；
8. 将访问方式写入团队文档。

产出：可访问的 Vercel 预览部署。

执行记录：[第 4 天步骤 7：Vercel 与远程环境审计记录](artifacts/day-4/DAY_4_STEP_7_VERCEL_ENVIRONMENT_AUDIT.md)。Production 已在最新环境设置下重新部署，受保护的 Preview deployment 也已建立；两者均为 `Ready`，根页面与 Supabase 健康接口均返回 HTTP `200`。现阶段 Preview 经用户明确批准共用现有 Supabase 项目，只同步公开 URL 与 publishable key，并限制为虚构数据和非破坏性测试。步骤 7 已完成。

检查：预览部署成功，页面可访问，环境变量范围正确。
