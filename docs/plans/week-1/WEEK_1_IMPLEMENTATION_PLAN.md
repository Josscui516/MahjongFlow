# MahjongFlow 5 日制周实现计划

## 课程第 2 周（开发第 1 周）：范围冻结与开发准备

> 本计划提炼自[《MVP 项目企划书》](../../project/MVP_PROJECT_PROPOSAL.md)第 9 节“9 周交付计划”，并按 5 个工作日组织。本周只建立后续开发所需的范围、设计、技术和协作基线，不进入业务功能开发。

## 1. 本周目标

建立清晰、可执行且经团队确认的开发基线，使项目从下一开发周起能够按排好优先级的 Product Backlog 开始实现。

## 2. 本周工作范围

### 2.1 冻结产品范围

- 团队共同审阅并确认 MVP 项目企划书；
- 确认 P0 必须交付范围及各用户故事的验收标准；
- 明确 P1 与非 MVP 边界；
- 将新增需求默认放入 Post-MVP Backlog，除非团队批准其等量替换现有范围；
- 记录尚未解决的范围问题、负责人和解决期限。

完成标准：团队对 P0、P1、非 MVP 边界和需求变更规则达成一致，P0 项目均具有可验证的验收条件。

### 2.2 建立项目管理与协作流程

- 创建并整理 Product Backlog；
- 建立 GitHub Project，使用以下 Kanban 状态：

  `Backlog → Ready → In Progress → Review → Testing → Done`

- 按 P0、P1、Post-MVP 标记优先级和范围；
- 为 backlog 条目补充用户价值、验收条件、依赖、负责人和工作量估算；
- 建立 feature、bug 等必要的 issue 模板；
- 明确分支、Pull Request 和代码审查规则；
- 约定阻塞超过 1 个工作日后的标记与升级方式。

完成标准：P0 backlog 已排序，近期任务可直接进入 `Ready`，团队成员能够依照统一模板创建 issue 和 Pull Request。

### 2.3 冻结技术栈与仓库结构

本周确认并冻结以下核心技术方案：

| 层级 | 采用方案 |
|---|---|
| Web 框架 | Next.js + TypeScript |
| UI | React + Tailwind CSS |
| 数据库 | Supabase PostgreSQL |
| 身份认证 | Supabase Auth |
| 权限 | Supabase RLS + 服务端鉴权 |
| 部署 | Vercel + Supabase |
| 版本管理 | GitHub + Pull Request |
| 项目管理 | GitHub Projects / Kanban |

- 确定应用代码、组件、数据库迁移、测试和文档的目录结构；
- 记录关键技术决策及其理由；
- 除非出现阻断性问题，后续开发周不更换核心框架、数据库或认证方案。

完成标准：技术栈和仓库结构已形成书面约定，团队成员能够在统一环境中安装并启动项目。

### 2.4 完成信息架构与低保真设计

- 列出 MVP 的主要页面及页面层级；
- 绘制主要页面流程，覆盖会议、决策转任务、任务跟进、活动、报名、签到和晚餐核验；
- 完成主要页面的低保真线框；
- 标注普通委员会成员、秘书／授权人员和活动参与者可进入的页面；
- 在线框中考虑加载、空状态、成功和错误反馈的位置。

完成标准：主要 P0 用户流程都能映射到页面，页面入口和角色可见范围清晰，不存在无法落地到界面的 P0 需求。

### 2.5 完成数据、权限与隐私设计

- 绘制数据库 ERD，至少包含：`profiles`、`meetings`、`discussion_points`、`meeting_decisions`、`tasks`、`events`、`participants`、`registrations`、`attendance_records`；
- 标明实体关系、外键、唯一约束和关键状态字段；
- 确认任务来源、活动关联、报名唯一性、签到唯一性和晚餐资格计算规则；
- 将企划书中的 MVP 权限矩阵整理为可实现、可测试的权限基线；
- 建立隐私字段清单，标记每个字段的用途、敏感级别、可访问角色和是否为必填；
- 确认开发及演示环境只使用虚构或匿名化数据。

完成标准：ERD、权限矩阵和隐私字段清单相互一致；敏感数据默认拒绝访问；每项敏感操作都明确服务端及数据库层的控制要求。

### 2.6 创建开发与部署环境

- 初始化可运行的 Next.js、TypeScript 和 Tailwind CSS 项目；
- 创建并连接 Supabase 开发环境；
- 创建 Vercel 开发／预览环境；
- 建立环境变量示例文件，确保密钥和真实生产配置不进入 Git；
- 验证新成员可依据 README 从干净环境完成安装和启动；
- 验证一次最小预览部署。

完成标准：本地项目可启动，Supabase 开发环境可连接，Vercel 预览部署可访问，仓库中不包含密钥或真实参与者数据。

### 2.7 建立工程质量基线

- 配置 lint；
- 配置 TypeScript typecheck；
- 选择并配置测试框架；
- 添加最小 smoke test；
- 配置 CI，在 Pull Request 上运行 lint、typecheck、测试和构建；
- 将 CI 通过设为进入 `Done` 的必要条件之一。

完成标准：本地与 CI 均能执行 lint、typecheck、自动化测试和构建；基线分支上的所有检查通过。

## 3. 5 个工作日实施安排

### 第 1 天：范围确认与技术基线冻结

当日目标：统一团队对“做什么、暂时不做什么、使用什么技术实现”的理解，为后续设计和任务拆分建立边界。

主要任务：

- 团队共同审阅 MVP 项目企划书；
- 确认 P0 用户故事、功能范围和验收标准；
- 明确 P1、非 MVP 和 Post-MVP 的边界；
- 确认新增需求必须进入 Post-MVP Backlog，或经批准后等量替换现有范围；
- 冻结 Next.js、TypeScript、React、Tailwind CSS、Supabase 和 Vercel 技术栈；
- 初步确定仓库目录、分支、Pull Request 和代码审查规则；
- 记录待确认事项、负责人和最迟解决时间。

当日输出：

- 已确认的 P0、P1 和非 MVP 范围清单；
- P0 验收标准清单；
- 技术栈与初步仓库结构说明；
- 范围变更及技术变更规则；
- 待解决问题记录。

执行结果：[第 1 天最终评审与签认记录](artifacts/DAY_1_FINAL_REVIEW_AND_SIGNOFF.md)。

完成检查：

- [x] 每个 P0 项目都有可验证的验收条件；
- [x] 团队对范围边界不存在未记录的关键分歧；
- [x] 核心技术栈已经确认，后续设计不再依赖技术选型决定；
- [x] 所有未解决事项都有负责人和截止时间。

### 第 2 天：Backlog、信息架构与页面流程

当日目标：把已冻结的产品范围转换为可追踪的工作项和可落地的页面结构。

主要任务：

- 创建 Product Backlog 和 GitHub Project；
- 配置 `Backlog → Ready → In Progress → Review → Testing → Done` 工作流；
- 将 P0 用户故事拆为可实施的 epic、issue 或任务；
- 为 backlog 条目补充优先级、验收条件、依赖、工作量估算和建议负责人；
- 建立 feature、bug 等必要的 issue 模板和 Pull Request 模板；
- 列出 MVP 页面并建立信息架构；
- 绘制会议、决策转任务、任务跟进、活动、报名、签到和晚餐核验的主要页面流程；
- 完成主要页面的低保真线框，并标注角色入口和加载、空状态、成功、错误反馈。

当日输出：

- 已配置的 GitHub Project；
- 排好优先级的 Product Backlog；
- issue 和 Pull Request 模板；
- 信息架构图；
- 主要页面流程和低保真线框。

完成检查：

- [ ] 所有 P0 需求都能追踪到 backlog 条目；
- [ ] 高优先级任务已标明验收条件和依赖；
- [ ] 所有主要 P0 用户流程都能映射到具体页面；
- [ ] 不同角色的页面入口和可见范围已经标明。

### 第 3 天：数据库、权限与隐私设计

当日目标：在开始编码前确认数据模型、安全边界和敏感信息处理规则。

主要任务：

- 绘制数据库 ERD；
- 定义核心实体的关键字段、主键、外键和状态字段；
- 确认任务来源、活动关联、报名唯一性和签到唯一性约束；
- 确认晚餐资格由签到状态计算，不作为可任意修改的独立数据源；
- 将 MVP 权限矩阵转换为可实现和可测试的访问规则；
- 明确前端路由、服务端处理和 Supabase RLS 各自承担的权限校验；
- 编制隐私字段清单，记录用途、敏感级别、可访问角色、必填性和保留原则；
- 设计虚构或匿名化种子数据方案；
- 交叉检查 ERD、权限矩阵、隐私字段和页面流程是否一致。

当日输出：

- 数据库 ERD；
- 数据实体和关键约束说明；
- MVP 权限矩阵；
- 隐私字段清单；
- 匿名化种子数据方案；
- 数据及权限设计评审记录。

完成检查：

- [ ] 每个 P0 数据需求都能映射到实体和字段；
- [ ] 敏感数据默认拒绝访问；
- [ ] 每项敏感操作都有服务端和数据库层的控制要求；
- [ ] ERD、权限矩阵、隐私字段和页面流程之间不存在冲突；
- [ ] 开发及演示不需要使用真实参与者数据。

### 第 4 天：项目骨架与开发环境搭建

当日目标：建立所有成员都能运行、连接和部署的统一项目环境。

主要任务：

- 初始化 Next.js、TypeScript 和 Tailwind CSS 项目；
- 按已确认的方案建立应用代码、组件、数据库、测试和文档目录；
- 创建并连接 Supabase 开发环境；
- 建立首个数据库迁移目录或迁移基线；
- 创建 Vercel 项目和开发／预览环境；
- 配置本地环境变量，并提供不含真实值的 `.env.example`；
- 编写项目安装、配置和启动说明；
- 由另一名成员按照说明执行一次干净安装；
- 完成一次最小预览部署并记录访问方式。

当日输出：

- 可启动的 Next.js 项目骨架；
- 已连接的 Supabase 开发环境；
- 数据库迁移基线；
- 可访问的 Vercel 预览部署；
- `.env.example`；
- 开发环境安装与启动说明；
- 干净安装验证记录。

完成检查：

- [ ] 项目可在至少两名成员的本地环境中启动；
- [ ] 应用能够连接 Supabase 开发环境；
- [ ] Vercel 预览部署可以访问；
- [ ] 仓库不包含密钥、生产配置或真实参与者数据；
- [ ] 仓库实际结构与第 1 天冻结的方案一致。

### 第 5 天：工程质量基线、周验收与下周准备

当日目标：确保项目骨架可持续开发，并完成本周所有基线成果的统一验收。

主要任务：

- 配置并运行 lint；
- 配置并运行 TypeScript typecheck；
- 选择和配置测试框架，添加最小 smoke test；
- 验证生产构建；
- 配置 CI，使 Pull Request 自动执行 lint、typecheck、测试和构建；
- 修复基线检查发现的问题；
- 对照本计划检查范围、Backlog、设计、数据、权限、隐私、环境和文档交付物；
- 将未完成或未通过的事项记录为阻塞项，不以口头约定代替；
- 为开发第 2 周选出首批任务，补齐验收条件、依赖和负责人，并移入 `Ready`；
- 召开周末评审，记录结论和遗留风险。

当日输出：

- 可运行的 lint、typecheck、测试和构建命令；
- 自动执行质量检查的 CI；
- 本周验收记录；
- 遗留问题和风险清单；
- 开发第 2 周的 `Ready` 任务列表。

完成检查：

- [ ] 本地和 CI 的 lint、typecheck、测试及构建全部通过；
- [ ] 本周所有交付物均有可访问的存放位置；
- [ ] 未完成项均已记录影响、负责人和处理时间；
- [ ] 开发第 2 周首批任务可以直接开始实施；
- [ ] 团队已经完成本周成果评审并记录结论。

### 5 日执行约束

- 每天开始时确认当日任务、依赖和负责人，结束时按“完成检查”逐项核对；
- 前一天未完成且会阻塞后续工作的任务，次日优先处理并在 GitHub Project 中标记；
- 阻塞超过 1 个工作日必须升级，不得静默顺延；
- 每人同时处于 `In Progress` 的主要任务不超过 1 个；
- 当日新增需求只记录到 backlog，不改变已冻结的本周目标；
- 第 5 天未通过周验收的基线事项不得直接标记为 `Done`。

## 6. 本周完成定义

只有在以下条件全部满足后，课程第 2 周（开发第 1 周）才视为完成：

1. 本周交付物已存入团队共享仓库或协作空间，并可由所有成员访问；
2. 范围、技术栈、ERD、权限矩阵和隐私清单不存在未记录的关键分歧；
3. 项目可由另一名成员依据文档从干净环境成功启动；
4. 基线分支的 lint、typecheck、测试和构建全部通过；
5. 预览环境可访问，且未暴露密钥、生产配置或真实参与者数据；
6. 下一开发周的任务已有明确验收条件、依赖和优先级，可以直接开始实施。

## 7. 本周明确不做

- 不实现会议、任务、Dashboard、活动、报名、签到或晚餐核验等业务功能；
- 不开发复杂的自定义权限编辑器；
- 不加入邮件、短信或推送通知；
- 不因未经批准的新需求扩大本轮 MVP；
- 不使用真实参与者数据进行开发或演示。
