# 第 1 天计划：范围确认与技术基线冻结

## 1. 当日目标

在当天结束前，让团队对 MVP 的交付范围、验收边界、技术选型、仓库结构和协作规则达成一致，为第 2 天的任务拆分及页面设计提供稳定输入。

## 2. 开始条件

- 所有参与者能够访问[《MVP 项目企划书》](../../project/MVP_PROJECT_PROPOSAL.md)；
- 已确定当天参加范围和技术评审的团队成员；
- 已准备一个共享的决策记录位置；
- 团队知道本周只进行范围、设计和工程基线准备，不实现业务功能。

## 3. 详细执行步骤

### 步骤 1：召开当天启动会议

1. 指定一名会议主持人和一名记录人；
2. 说明当天必须完成的五类结果：范围、验收标准、技术栈、仓库结构、协作规则；
3. 确认所有争议都必须写入待解决事项，不依赖口头记忆；
4. 规定评审结束时间及最终确认方式。

产出：当天议程、参与者名单和决策记录文档。

执行记录：[第 1 天启动会议议程与决策记录](artifacts/day-1/DAY_1_KICKOFF_MEETING.md)。

检查：每项议题都有明确的讨论时段及负责推动结论的人。

### 步骤 2：逐项核对 P0 范围

1. 从企划书第 6.1 节提取全部 P0 模块；
2. 按认证、会议、决策转任务、任务与 Dashboard、活动、报名、签到、晚餐核验分组；
3. 为每项功能确认目标用户和业务价值；
4. 检查是否存在重复、含义不清或依赖未说明的条目；
5. 将确认后的条目标记为“本轮必须交付”；
6. 对有争议的条目记录问题、影响、负责人和当天解决期限。

产出：经确认的 P0 功能清单。

执行记录：[第 1 天 P0 功能范围清单](artifacts/day-1/DAY_1_P0_SCOPE_CHECKLIST.md)。

检查：企划书中的每个 P0 项目都已进入清单，没有遗漏或私自新增功能。

### 步骤 3：核对用户故事与验收标准

1. 将每个 P0 项目关联到对应用户故事；
2. 检查每条用户故事是否说明角色、需求和价值；
3. 将验收条件改写为可以观察或测试的结果；
4. 同时检查成功路径、失败路径和无权限路径；
5. 标记需要通过数据库约束或权限测试验证的条件；
6. 对无法验证的描述补充明确的输入、操作和预期结果。

产出：P0 需求—用户故事—验收条件对照表。

执行记录：[第 1 天 P0 用户故事与验收矩阵](artifacts/day-1/DAY_1_P0_ACCEPTANCE_MATRIX.md)。

检查：任何成员都能根据验收条件判断功能是通过还是失败。

### 步骤 4：冻结 P1、非 MVP 与需求变更边界

1. 列出 P1 项目并确认它们不阻塞 P0 验收；
2. 列出明确不在 MVP 内的功能；
3. 建立 Post-MVP Backlog 分类；
4. 规定新需求默认进入 Post-MVP Backlog；
5. 规定只有团队正式批准等量替换现有范围时，新需求才能进入本轮 MVP；
6. 指定范围变更记录必须包含提出人、理由、影响、替换项和批准结论。

产出：范围边界清单和需求变更规则。

执行记录：[第 1 天范围边界与需求变更规则](artifacts/day-1/DAY_1_SCOPE_BOUNDARIES_AND_CHANGE_CONTROL.md)。

检查：团队能够明确回答“某项新需求应该放在哪里、由谁批准、会替换什么”。

### 步骤 5：确认并冻结核心技术栈

1. 确认 Web 框架采用 Next.js 与 TypeScript；
2. 确认 UI 采用 React 与 Tailwind CSS；
3. 确认数据库与认证采用 Supabase PostgreSQL 和 Supabase Auth；
4. 确认敏感权限由 Supabase RLS 与服务端鉴权共同执行；
5. 确认部署采用 Vercel 与 Supabase；
6. 确认版本管理及项目管理采用 GitHub、Pull Request 和 GitHub Projects；
7. 记录每项选型的用途、采用理由和已知风险；
8. 规定除阻断性问题外，后续开发周不更换核心技术。

产出：技术栈决策记录。

执行记录：[第 1 天核心技术栈决策记录](artifacts/day-1/DAY_1_TECH_STACK_DECISION.md)。

检查：不存在两个功能相同但尚未决定使用哪一个的核心工具。

### 步骤 6：设计仓库结构基线

1. 确认使用单一 Next.js 应用仓库；
2. 规划应用路由、共享组件、业务模块、工具函数和类型定义的目录；
3. 规划 Supabase 迁移、种子数据和权限策略的目录；
4. 规划单元测试、集成测试和端到端测试的存放位置；
5. 规划产品、架构、权限和运行说明文档的目录；
6. 记录命名规则和禁止提交的文件类型；
7. 检查该结构能支持后续所有 P0 模块。

产出：仓库目录草图和命名约定。

执行记录：[第 1 天仓库结构与命名基线](artifacts/day-1/DAY_1_REPOSITORY_STRUCTURE_BASELINE.md)。

检查：每类预计产生的代码、数据库文件、测试和文档都有明确位置。

### 步骤 7：确定 Git 与协作规则

1. 约定短生命周期功能分支的命名方式；
2. 规定每个 Pull Request 必须关联 issue 和验收标准；
3. 规定至少一名其他成员进行代码审查；
4. 规定数据库或权限变更必须包含迁移、回滚说明和权限测试；
5. 规定禁止提交密钥、生产配置和真实参与者数据；
6. 规定每人同时处于 `In Progress` 的主要任务不超过一个；
7. 规定阻塞超过一个工作日必须在项目板标记并升级。

产出：团队协作约定初稿。

执行记录：[第 1 天 Git 与团队协作约定](artifacts/day-1/DAY_1_GIT_COLLABORATION_AGREEMENT.md)。

检查：团队成员知道如何开始任务、提交变更、请求审查和报告阻塞。

### 步骤 8：完成当日评审与签认

1. 按 P0 清单逐项确认范围；
2. 抽查验收标准是否可测试；
3. 逐项确认技术栈和仓库结构；
4. 汇总未解决事项并评估是否阻塞第 2 天；
5. 为遗留事项指定负责人和最迟解决时间；
6. 记录团队确认结论，并将文档保存到共享仓库。

产出：第 1 天评审记录和已批准的基线文档。

执行记录：[第 1 天最终评审与签认记录](artifacts/day-1/DAY_1_FINAL_REVIEW_AND_SIGNOFF.md)。

检查：第 2 天可以直接依据已确认范围创建 backlog 和页面流程。

## 4. 当日交付物

- P0、P1、非 MVP 和 Post-MVP 范围清单；
- P0 需求—用户故事—验收条件对照表；
- 范围变更规则；
- 技术栈决策记录；
- 仓库目录草图与命名约定；
- Git 与协作规则；
- 决策、问题和风险记录。

- [x] 未解决事项都有负责人和截止时间；

## 6. 未完成项处理

- 范围或技术栈的阻断性争议必须在第 2 天开始前解决；
- 非阻断性文字完善可以登记为任务，但不得改变已批准范围；
- 无负责人、无截止时间的遗留问题不得视为已处理；
- 如果某项新需求无法归类，默认进入 Post-MVP Backlog。
