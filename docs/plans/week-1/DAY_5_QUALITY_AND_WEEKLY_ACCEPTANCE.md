# 第 5 天计划：工程质量基线、周验收与下周准备

## 1. 当日目标

建立自动化工程质量基线，验证本周所有交付物，明确处理遗留问题，并让开发第 2 周的首批任务达到可直接开始的 `Ready` 状态。

## 2. 开始条件

- Next.js 项目能够在本地启动并完成生产构建；
- Supabase 开发环境和 Vercel 预览环境可用；
- 安装说明和 `.env.example` 已完成初稿；
- 范围、Backlog、页面流程、ERD、权限矩阵和隐私字段清单可访问；
- 第 1 至第 4 天的遗留问题和风险均已有记录。

## 3. 详细执行步骤

### 步骤 1：汇总并分级现有问题

1. 收集第 1 至第 4 天的全部未完成项；
2. 去除重复问题并补充问题描述；
3. 按“阻断本周验收”“阻断下周开发”“非阻断改进”分类；
4. 评估每项问题的影响和处理工作量；
5. 为每项问题指定负责人和处理期限；
6. 优先处理本地启动、构建、连接、权限设计缺口和密钥风险；
7. 将无法当天解决但不阻断的事项放入 backlog。

产出：经过分级的遗留问题与风险清单。

检查：不存在无负责人或无法判断影响的遗留问题。

执行记录：[第 5 天步骤 1：遗留问题与风险分级清单](artifacts/day-5/DAY_5_STEP_1_OUTSTANDING_ISSUES_AND_RISKS.md)。已从第 1 至第 4 天的计划、执行产物、周验收与 Week 2 开始条件中去重汇总 10 项：3 项阻断本周验收、3 项阻断下周开发、4 项非阻断改进；每项均已记录影响、工作量、负责人、期限和处理证据。未执行未经授权的 GitHub、Git 或远程配置写操作。

### 步骤 2：配置并验证 lint

1. 检查项目当前的 lint 配置；
2. 确认它覆盖应用代码、配置文件和测试代码；
3. 排除生成文件、构建输出和不应检查的目录；
4. 在包管理脚本中提供统一的 lint 入口；
5. 对当前项目运行 lint；
6. 修复全部错误；
7. 对需要保留的例外写明理由，避免无说明地全局关闭规则；
8. 再次运行并记录通过结果。

产出：可重复运行且通过的 lint 配置与脚本。

检查：团队成员使用同一入口能得到一致结果，基线代码无 lint 错误。

执行记录：[第 5 天步骤 2：lint 配置与验证记录](artifacts/day-5/DAY_5_STEP_2_LINT_BASELINE.md)。项目保留 Next.js Core Web Vitals 与 TypeScript 推荐规则，统一入口明确为 `npm run lint` → `eslint .`，并补齐生成文件、构建输出、测试报告及本地平台状态的忽略范围；没有关闭规则或增加无说明例外。

### 步骤 3：配置并验证 typecheck

1. 检查 TypeScript 严格性设置是否符合项目基线；
2. 确认应用代码和必要测试代码进入类型检查范围；
3. 在包管理脚本中建立独立的 typecheck 入口；
4. 运行 typecheck；
5. 修复隐式 `any`、错误导入和不安全类型等问题；
6. 避免仅用宽泛类型绕过错误；
7. 再次运行并记录通过结果。

产出：可重复运行且通过的 typecheck 配置与脚本。

检查：类型检查可以独立于开发服务器运行，当前代码无类型错误。

执行记录：[第 5 天步骤 3：typecheck 配置与验证记录](artifacts/day-5/DAY_5_STEP_3_TYPECHECK_BASELINE.md)。现有 `tsconfig.json` 已启用完整 `strict` 与 `noEmit`，应用、配置、Next.js 生成类型及未来的 TypeScript 测试均在检查范围内；统一入口为 `npm run typecheck` → `next typegen && tsc --noEmit`，可在没有旧 `.next` 输出时先生成路由类型再检查，D5-OI-01 已关闭。

### 步骤 4：配置测试框架和最小 smoke test

1. 根据项目技术栈选择测试框架；
2. 建立测试配置和统一测试入口；
3. 建立测试文件命名及目录约定；
4. 添加一个验证项目基础行为的最小 smoke test；
5. 确保测试不依赖真实外部数据或生产服务；
6. 运行测试并修复配置问题；
7. 故意制造一次可控失败，确认失败会返回非零结果；
8. 恢复测试并再次运行通过。

产出：测试框架、测试脚本和通过的 smoke test。

检查：测试成功与失败都能被命令行和后续 CI 正确识别。

执行记录：[第 5 天步骤 4：测试框架与 smoke test 验证记录](artifacts/day-5/DAY_5_STEP_4_TEST_FRAMEWORK_AND_SMOKE_TEST.md)。项目已采用 Vitest 4.1.10，建立 `npm test` → `vitest run` 和 Node 环境测试配置；最小 smoke test 只使用虚构本地配置，已验证成功退出码 `0`、可控失败退出码 `1` 以及恢复后的再次通过。D5-OI-02 的本地测试部分已完成，CI 部分留待步骤 6。

### 步骤 5：验证生产构建

1. 清理本地构建输出；
2. 使用与部署环境一致的构建入口执行生产构建；
3. 检查构建日志中的错误和警告；
4. 修复会影响部署、类型安全或运行时行为的问题；
5. 确认构建不需要未记录的本地变量；
6. 再次执行构建并记录结果；
7. 对照 Vercel 构建确认行为一致。

产出：通过的本地生产构建记录。

检查：干净环境和 Vercel 均能使用已记录配置完成构建。

执行记录：[第 5 天步骤 5：生产构建验证记录](artifacts/day-5/DAY_5_STEP_5_PRODUCTION_BUILD_VERIFICATION.md)。已在 `npm ci` 后两次核实并清理仓库内 `.next`，修正干净输出下路由类型未生成的 typecheck 入口，再完成 lint、typecheck、smoke test 和最终 `npm run build`；Next.js 16.3.0/Turbopack 构建无错误或警告并生成 `BUILD_ID`。最新 Vercel Production 为同一 HEAD、状态 `READY`，版本、bundler、入口和路由输出一致，根页面与 Supabase 健康接口均为 HTTP `200`；未部署当前未提交变更。

### 步骤 6：建立 CI 工作流

1. 创建针对 Pull Request 和基线分支更新的 CI 工作流；
2. 配置检出代码、准备运行时和安装锁定依赖；
3. 按顺序执行 lint、typecheck、测试和构建；
4. 配置必要的非敏感测试环境变量；
5. 确认 CI 不使用生产密钥或真实数据；
6. 提交一个测试 Pull Request 触发工作流；
7. 检查每个步骤的日志和状态；
8. 制造一次安全的临时失败以确认 CI 能阻止错误通过，随后撤销并重新运行；
9. 在仓库设置允许的情况下，将必要检查设为合并条件。

产出：能够自动执行四项质量检查的 CI 工作流。

检查：Pull Request 上可以清楚看到每项检查结果，失败会阻止达到完成条件。

执行记录：[第 5 天步骤 6：CI 工作流与必需检查验证记录](artifacts/day-5/DAY_5_STEP_6_CI_WORKFLOW_AND_REQUIRED_CHECKS.md)。已建立 `Quality` workflow，在 Draft PR #43 上依次显示 `Lint`、`Typecheck`、`Test`、`Build`；完成初始全绿、虚构 smoke test 临时失败（Test 失败、Build 跳过、PR `UNSTABLE`）和恢复后全绿三次远程验证。`main` 已将四项检查配置为 strict required checks 并对管理员生效；工作流只使用只读仓库权限和虚构 localhost 公共配置。D5-OI-02 已关闭，非作者 required review 仍留在 D5-OI-04。

### 步骤 7：检查仓库卫生与安全

1. 查看所有新增和修改文件；
2. 检查是否包含本地环境文件、密钥、token 或生产配置；
3. 检查是否包含真实姓名、邮箱、学号或签到资料；
4. 检查构建输出、依赖目录和临时文件是否被错误追踪；
5. 检查 `.env.example` 只有变量名、占位值和说明；
6. 检查 README 不暴露敏感信息；
7. 修复发现的问题并再次检查。

产出：仓库卫生与安全检查记录。

检查：待交付项目骨架可以安全共享和部署到预览环境。

### 步骤 8：执行周级交付物验收

1. 打开[《第 1 周实现计划》](WEEK_1_IMPLEMENTATION_PLAN.md)的周验收清单；
2. 逐项找到范围、Backlog、模板、技术决策、线框、ERD、权限和隐私文档；
3. 对每项交付物记录存放位置和评审状态；
4. 验证项目本地启动、Supabase 连接和 Vercel 预览部署；
5. 验证 lint、typecheck、测试、构建和 CI；
6. 抽查 P0 需求能否追踪到验收标准、backlog、页面与数据设计；
7. 不满足条件的条目保持未勾选，并创建问题；
8. 形成周验收结果。

产出：带证据和链接的周验收记录。

检查：每个已勾选项目都有实际产出或验证结果支持。

### 步骤 9：准备开发第 2 周首批任务

1. 根据 9 周计划选择认证、权限和数据基础相关任务；
2. 检查每项任务是否属于 P0；
3. 补充用户故事、验收条件和界面／数据设计链接；
4. 补充依赖、负责人和工作量估算；
5. 补充需要覆盖的成功、失败和权限测试；
6. 确认任务不会依赖尚未解决的阻断项；
7. 将满足条件的任务移动到 `Ready`；
8. 保持信息不完整的任务在 `Backlog`。

产出：开发第 2 周首批 `Ready` 任务列表。

检查：负责人可以在下一工作日直接开始，无需重新确认范围或依赖。

### 步骤 10：召开周末评审并完成交接

1. 演示本地项目和 Vercel 预览环境；
2. 展示 Product Backlog、主要页面流程和线框；
3. 展示 ERD、权限矩阵和隐私字段清单；

8. 记录团队的接受、保留意见或未通过结论；
9. 将评审记录保存到共享仓库或项目空间。

产出：周末评审记录和开发第 2 周交接结论。

检查：所有成员知道本周完成状态、现存风险和下周第一批工作。

## 6. 本周通过条件

只有同时满足以下条件，本周才可标记为完成：

1. 范围、技术栈、ERD、权限矩阵和隐私字段清单已经确认；
2. 项目可由另一名成员从干净环境安装、启动和构建；
3. Supabase 开发环境和 Vercel 预览环境可用；
4. lint、typecheck、测试、构建和 CI 全部通过；
5. 仓库中不存在密钥、真实参与者数据或生产配置；
6. 所有阻断性问题已经解决；
7. 开发第 2 周的首批任务可以直接开始。

## 7. 未完成项处理

- 任何阻断性质量检查失败都必须保留为“未通过”，不得为了按时结束而跳过；
- 如果只有非阻断文档改进未完成，应创建带负责人和期限的 backlog 条目；
- 如果项目无法干净安装、构建或部署，本周不能标记完成；
- 如果权限或隐私基线仍有冲突，不得开始依赖该规则的功能实现；
- 所有新增功能建议继续进入 Post-MVP Backlog，不改变下周既定 P0 范围。
