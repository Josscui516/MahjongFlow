# 第 2 天计划：Backlog、信息架构与页面流程

## 1. 当日目标

把第 1 天冻结的范围转换为可追踪、可排期的 Product Backlog，并建立覆盖全部 P0 流程的信息架构、页面流程和低保真线框。

## 2. 开始条件

- 第 1 天的 P0 范围与验收标准已经确认；
- 技术栈和仓库结构基线已经确定；
- 团队可以访问 GitHub 仓库和 GitHub Projects；
- 范围争议已解决，或已经明确为不阻塞当天工作的遗留事项。

## 3. 详细执行步骤

### 步骤 1：建立项目板和工作流

1. 创建 MahjongFlow MVP 的 GitHub Project；
2. 建立 `Backlog`、`Ready`、`In Progress`、`Review`、`Testing`、`Done` 状态；
3. 添加优先级字段，至少区分 P0、P1 和 Post-MVP；
4. 添加模块、负责人、工作量、依赖和目标开发周等字段；
5. 建立默认视图，使团队能按状态、优先级和模块查看任务；
6. 检查团队成员是否具有正确的查看和编辑权限。

产出：可用的 GitHub Project 和 Kanban 工作流。

检查：创建一个测试任务并完整移动各状态，确认字段和权限正常。

执行结果：[步骤 1：GitHub Project 与工作流配置记录](artifacts/day-2/DAY_2_STEP_1_PROJECT_BOARD_SETUP.md)。

### 步骤 2：建立 issue 与 Pull Request 模板

1. 创建 feature issue 模板；
2. 在模板中加入背景、用户故事、范围、验收条件、依赖和测试要求；
3. 创建 bug issue 模板；
4. 在模板中加入复现步骤、实际结果、预期结果、严重程度和环境；
5. 创建 Pull Request 模板；
6. 在模板中加入关联 issue、变更说明、测试证据、权限／隐私检查和数据库迁移说明；
7. 使用模板各创建一个示例并检查字段是否足够。

产出：feature、bug 和 Pull Request 模板。

检查：模板能够支持协作者在不口头补充背景的情况下理解任务或变更。

执行结果：[步骤 2：Issue 与 Pull Request 模板及验证记录](artifacts/day-2/DAY_2_STEP_2_ISSUE_AND_PR_TEMPLATES.md)。

### 步骤 3：将 P0 范围拆分为 backlog

1. 以认证、会议、决策转任务、任务与 Dashboard、活动、报名、签到和晚餐核验建立模块或 epic；
2. 将每个 P0 用户故事拆为用户可感知且可独立验收的任务；
3. 把数据库、权限、错误状态和测试工作纳入对应任务，不单独遗忘；
4. 为每项任务粘贴或关联验收条件；
5. 标记前置依赖和后续依赖；
6. 给出相对工作量估算；
7. 将超出单个短周期的任务继续拆小；
8. 检查所有 P0 条目都至少关联一个实施任务和一个验证方式。

产出：覆盖全部 P0 的初始 Product Backlog。

检查：从任一 P0 需求都能追踪到对应任务、验收条件和验证方式。

执行结果：[步骤 3：P0 Product Backlog 与覆盖审计记录](artifacts/day-2/DAY_2_STEP_3_P0_PRODUCT_BACKLOG.md)。

### 步骤 4：排序 backlog

1. 优先排列认证、数据库和权限等共享基础；
2. 按“会议 → 决策转任务 → 任务跟进”安排核心协调流程；
3. 在核心协调流程后安排活动、报名、签到和晚餐核验；
4. 将高风险数据与权限验证放在相应功能实现的同一阶段；
5. 标出可以并行的 UI、数据和测试任务；
6. 将尚未满足依赖的任务保留在 `Backlog`；
7. 只将范围、依赖和验收条件清晰的近期任务放入 `Ready`。

产出：按价值、依赖和风险排序的 backlog。

检查：排序结果与企划书的 9 周交付顺序一致，没有让后续模块阻塞基础模块。

执行结果：[步骤 4：排序后的 P0 Backlog 与 Ready 决策记录](artifacts/day-2/DAY_2_STEP_4_PRIORITISED_BACKLOG.md)。

### 步骤 5：建立页面清单和信息架构

1. 列出公共页面、委员会后台页面和授权人员敏感页面；
2. 为每个页面记录用途、主要角色、入口和可执行操作；
3. 确定全局导航及各业务模块的层级；
4. 标记需要受保护路由的页面；
5. 标记只允许秘书／授权人员访问的敏感页面；
6. 标记参与者通过活动 token 进入的受限页面；
7. 检查每项 P0 操作是否有明确页面承载。

产出：页面清单和信息架构图。

检查：不存在有需求但无页面入口，或有页面但无明确角色的情况。

执行结果：[步骤 5：P0 页面清单与信息架构](artifacts/day-2/DAY_2_STEP_5_PAGE_INVENTORY_AND_INFORMATION_ARCHITECTURE.md)。

### 步骤 6：绘制核心用户流程

1. 绘制委员会成员登录和进入后台的流程；
2. 绘制创建会议、记录讨论点和关键决策的流程；
3. 绘制从会议决策创建任务并返回来源会议的流程；
4. 绘制查看本人任务、临期和逾期任务的流程；
5. 绘制创建活动、登记参与者和报名的流程；
6. 绘制参与者使用 QR 入口签到的流程；
7. 绘制授权人员人工补签、更正和核验晚餐资格的流程；
8. 为每条流程补充失败、重复提交、过期 token 和无权限分支。

产出：覆盖主要成功与失败路径的用户流程图。

检查：每条流程都注明起点、角色、关键操作、系统反馈和结束状态。

执行结果：[步骤 6：P0 核心用户流程](artifacts/day-2/DAY_2_STEP_6_CORE_USER_FLOWS.md)。

### 步骤 7：制作低保真线框

1. 从 Dashboard、会议列表／详情、任务列表／详情、活动列表／详情开始；
2. 补充登录、报名、签到和晚餐核验页面；
3. 在每个页面标出标题、导航、主要操作、表单、列表和状态信息；
4. 标出加载、空状态、成功、验证错误、权限拒绝和系统错误反馈；
5. 标出普通委员会成员与授权人员看到的差异；
6. 检查桌面和窄屏下的基本内容优先级；
7. 为每个线框关联对应的 backlog 或用户故事。

产出：主要页面低保真线框。

检查：团队可以仅根据线框说明页面的核心信息、操作和角色差异。

执行结果：[步骤 7：P0 低保真线框](artifacts/day-2/DAY_2_STEP_7_LOW_FIDELITY_WIREFRAMES.md)。

### 步骤 8：进行范围追踪与当日评审

1. 建立 P0 需求、backlog、页面和流程之间的追踪关系；
2. 检查是否有重复任务或遗漏任务；
3. 检查线框是否意外加入 P1 或非 MVP 功能；
4. 检查每个敏感页面是否正确标记访问角色；
5. 收集团队反馈并只修正已批准的 P0 流程；
6. 将新增想法放入 Post-MVP Backlog；
7. 保存评审结论并确定第 3 天需要重点验证的数据及权限问题。

产出：第 2 天评审记录和待第 3 天验证的问题清单。

检查：第 3 天能够根据页面与流程直接推导数据实体、字段和权限规则。

执行结果：[步骤 8：范围追踪与当日评审](artifacts/day-2/DAY_2_STEP_8_TRACEABILITY_AND_DAY_REVIEW.md)。
