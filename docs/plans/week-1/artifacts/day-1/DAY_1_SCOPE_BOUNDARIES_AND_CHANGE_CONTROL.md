## 1. 范围层级

| 层级 | 含义 | 当前处理规则 |
|---|---|---|
| P0 | MVP 验收所必需的功能、权限、数据与质量基线 | 本轮必须交付；不得因新增需求而静默删除或降级 |
| P1 | 企划书已识别的可选增强 | 不阻塞 P0；只有确认有余量且不威胁 P0 时才可进入 `Ready` |
| Post-MVP Backlog | MVP 验证后才评估的增强或新需求 | 默认存放所有新增需求；不承诺本轮实现 |
| 非 MVP | 已明确排除，或需要重新立项的大范围能力 | 本轮不设计、不拆实现任务、不纳入验收 |

## 2. P1 清单及非阻塞检查

| ID | P1 项目 | 不阻塞 P0 的理由 | P0 已提供的最低可用路径 | 状态 |
|---|---|---|---|---|

结论：7 项 P1 均有不依赖该增强的 P0 最低可用路径，因此没有任何 P1 项目阻塞 P0 验收。

### P1 启动条件

P1 项目只有同时满足以下条件才能从 Post-MVP/P1 候选移入本轮 `Ready`：

1. 相关 P0 路径已经完成并通过对应验收条件；
2. 当前不存在被该 P1 占用人员或环境所阻塞的 P0；
3. 已估算工作量、依赖、测试和权限影响；
4. 团队形成书面一致结论；
5. 项目板明确标记为 `P1`，不得伪装成 P0 缺陷或隐含子任务。

## 5. 新需求归类规则

收到新需求时按以下顺序判断：

1. 若它只是修复某项现有 P0 验收失败，归入 P0 缺陷，不算新增范围；
2. 若它已逐字或等价包含在 P0 清单中，关联现有 P0 ID，不重复创建范围项；
3. 若它属于 P1-01 至 P1-07，标记为 P1 候选并检查 P1 启动条件；
4. 其他新增能力一律进入对应 Post-MVP 分类；
5. 若属于 NMVP-01 至 NMVP-11，标记“非 MVP／需重新立项”，不得进入本轮实现；
6. 只有完成第 6 节的正式等量替换流程，新需求才可能进入本轮 MVP。

## 6. 本轮 MVP 等量替换流程

### 6.1 提出与记录

- 团队成员或 Stakeholder 均可提出需求；
- 当前范围记录负责人为 Day 1 主持人 Joshua Xingjian Cui；后续可由项目板明确指派的范围负责人接替；
- 提出后先记录到 Post-MVP Backlog，不因口头讨论直接进入 P0 或 `Ready`；
- Stakeholder 建议是重要输入，但不自动改变已批准范围。

### 6.2 必填变更记录

每项范围变更记录必须包含：

| 必填字段 | 内容要求 |
|---|---|
| 变更 ID | 使用 `CR-年份-三位序号`，例如 `CR-2026-001` |
| 提出人和提出时间 | 真实姓名、角色及时间 |
| 新需求描述 | 说明用户、需求、价值和可测试结果 |
| 提出理由 | 说明现有 P0 为什么不能满足目标 |
| 影响分析 | 工作量、排期、依赖、数据、隐私、权限、测试、部署和文档影响 |
| 建议替换项 | 指定一个或多个现有 P0/P1 ID，并证明工作量和风险大致等量 |
| 验收影响 | 列出新增、修改或删除的验收场景 ID |
| 风险与回退 | 说明失败时如何恢复已批准基线 |
| 批准结论 | `批准`、`拒绝` 或 `留在 Post-MVP`，并写明理由 |
| 批准人和时间 | 记录五名团队成员的书面结论及最终时间 |

缺少任一必填字段的变更请求不得进入评审。

### 6.3 影响评审

1. 范围负责人检查是否为真实新增需求或现有 P0 缺陷；
2. 技术负责人评估架构、数据、权限和部署影响；
3. 测试／记录负责人评估验收场景和回归范围；
4. 团队比较新增需求与建议替换项的工作量、风险和用户价值；
5. 若找不到明确且大致等量的替换项，结论只能是“留在 Post-MVP”或“拒绝”。

### 6.4 批准规则

- 批准主体是 MahjongFlow 五名项目团队成员，不是单一个人；
- 必须由五名成员书面一致同意，任何未解决异议都会使需求继续留在 Post-MVP；
- 批准结论必须明确写出被替换项，不接受“有时间就做”作为 P0 范围变更；
- 批准后必须同步更新 P0 清单、用户故事与验收矩阵、Backlog、排期和风险记录；
- 未完成上述同步前，新需求不得进入 `Ready` 或 `In Progress`。

### 6.5 不可交换基线

无论进度或新增需求如何，以下项目不得作为范围交换项：

- 服务端身份和权限检查；
- 敏感数据访问限制；
- Supabase RLS 或等效数据库权限保护；
- 数据库唯一约束和迁移；
- 会议决策到任务的可追踪关系；
- 核心端到端验收与回归测试；
- 不使用真实参与者数据的隐私要求。

## 7. 变更状态与处理期限

| 状态 | 含义 | 下一步 |
|---|---|---|
| `Proposed` | 已记录，尚未完成影响分析 | 补齐必填字段 |
| `Post-MVP` | 已归类但不进入本轮 | MVP 验证后再排序 |
| `Under Review` | 影响与替换项齐备 | 五名成员书面评审 |
| `Approved` | 已完成一致批准和等量替换 | 同步所有基线后进入 Backlog |
| `Rejected` | 不符合目标、不可行或不值得实施 | 保留结论，关闭请求 |

对当前工作造成阻塞的澄清应在一个工作日内升级，但不得以“紧急”为由绕过变更规则。
