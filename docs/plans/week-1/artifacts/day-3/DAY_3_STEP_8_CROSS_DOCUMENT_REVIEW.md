## 1. 评审结论

本轮逐项复核了 6 条 P0 用户故事、48 个 P0／强制隐私 ID、16 个页面、
7 条核心流程、13 份低保真线框、11 个业务实体以及 Auth 外部身份边界。
结论如下：

- 6 条用户故事全部能映射到已定义实体、字段、约束和权限控制；
- 16 个页面的业务读取、业务写入、临时输入和派生结果边界均已明确；
- 普通委员会响应中没有参与者姓名、邮箱、学号、报名或签到明细；
- token 参与者只能读取当前活动最小上下文并提交本人签到；
- 晚餐资格、到期状态、活动进度和人数均为派生值，没有重复可编辑事实；
- ERD 没有缺少 P0 验收所需的实体、关系、字段或唯一约束；
- 步骤 7 的 migration 顺序和虚构 seed 场景足以作为后续实施规格；
- 第 2 天留下的 PG-03 身份字段占位已同步为最终协议。

没有扩大到公开报名、通知、角色管理、永久删除、独立晚餐资格、短信、付款
或其他 Post-MVP 范围。第 3 天的 9 项当日验收全部通过。

## 6. ERD、约束和派生规则复核

| 验收关系／不变量 | ERD／规则承载 | 结果 |
|---|---|---|
| 一个会议有多名后台参与者 | `meeting_attendees` 连接表，组合主键 | 通过 |
| 讨论点与决策保留会议内顺序 | 子表外键及 `(meeting_id, sort_order)` 唯一 | 通过 |
| 任务可独立或来自一个具体来源 | `source_meeting_id` 加两个可空具体来源字段及检查约束 | 通过 |
| 同一来源不得并发创建两项任务 | 两个非空来源唯一部分索引 | 通过 |
| 一个任务最多关联一个活动 | `tasks.event_id` 单外键 | 通过 |
| 一个参与者每活动最多一条报名／签到 | 两个 `(event_id, participant_id)` 唯一约束 | 通过 |
| QR 签到要求有效报名，Manual 可处理 walk-in | 窄函数按 `method` 分支并重验 | 通过 |
| 旧 token 轮换后失效且明文不入库 | 独立 token 表、SHA-256 摘要、每活动一条 active token | 通过 |
| 取消／更正不删除历史 | 显式状态 `cancelled`／`voided` | 通过 |
| 到期、进度、人数、转换和资格不会漂移 | 全部从事实字段实时派生 | 通过 |

ERD 的 11 个业务实体已经足够支撑 P0。未发现需要在第 4 天前新增的表或字段。

## 7. 隐私清单与权限矩阵一致性

| 数据类别 | `committee` | `authorised` | token 参与者 | 匿名／未认证 | 结论 |
|---|---|---|---|---|---|
| 会议、任务、活动基础资料 | 后台范围读写 | 后台范围读写 | 仅有效 token 对应活动的最小上下文 | 拒绝 | 一致 |

| 报名与签到明细 | 拒绝 | 按用途读写／更正 | 仅得到本次通用结果 | 拒绝 | 一致 |
| 个人晚餐资格 | 拒绝 | 只读派生结果 | 拒绝 | 拒绝 | 一致 |
| token 明文／摘要 | 拒绝 | 仅窄服务端操作；明文只在生成时返回 | URL 中提交明文 | 拒绝 | 一致 |

住址、付款资料、营销同意等无 P0 用途字段继续明确禁止收集。
